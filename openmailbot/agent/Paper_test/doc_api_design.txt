API Design and REST Conventions

Resource-Oriented Design
========================
REST APIs follow resource-oriented design principles. Each resource is identified by a unique URI. Resources are collections (e.g., /products) or individual items (e.g., /products/123). Standard HTTP methods map to operations: GET retrieves resources, POST creates new resources, PUT updates existing resources, DELETE removes resources, PATCH partially updates resources.

Endpoint Naming Conventions
============================
Collection endpoints use plural nouns: GET /users, POST /users. Individual resource endpoints append an ID: GET /users/42. Nested resources follow the pattern /resource/ID/subresource: GET /users/42/orders. Query parameters filter, sort, and paginate: GET /products?category=electronics&sort=price&limit=20&offset=40.

Request and Response Formats
=============================
All data is exchanged in JSON format with UTF-8 encoding. Request bodies clearly specify the operation intent. Response bodies include requested data plus metadata. Responses always have a consistent structure with status, data, and optional error fields. Timestamps use ISO 8601 format.

HTTP Status Codes
=================
Success responses use 200 OK for standard success, 201 Created for resource creation, 204 No Content for empty responses. Client errors use 400 Bad Request for malformed input, 401 Unauthorized for missing auth, 403 Forbidden for insufficient permissions, 404 Not Found for missing resources, 409 Conflict for duplicate key errors. Server errors use 500 Internal Server Error for unexpected failures, 503 Service Unavailable for maintenance.

Error Handling
==============
Error responses include an error code for programmatic identification, a human-readable message, and a detailed description. Validation errors list specific fields that failed. Errors are logged with correlation IDs for tracing. Clients implement exponential backoff for retrying failed requests. Circuit breakers prevent cascading failures.

Pagination and Sorting
======================
Large result sets use cursor-based pagination with next/previous links. Limit and offset parameters control page size: limit=20, offset=100. Sorting uses the sort parameter: sort=-created_at for descending, sort=name for ascending. Multiple sort fields are comma-separated: sort=category,-price. The response includes total count and current page information.

Versioning Strategy
===================
API versioning uses URL paths: /v1/products, /v2/products. Major versions indicate breaking changes. Minor versions are backward compatible. Deprecation warnings are sent 6 months before retiring old versions. Clients specify a required API version in the Accept header. New endpoints are added incrementally without breaking existing clients.
